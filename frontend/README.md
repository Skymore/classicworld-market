# Maple Market React frontend

React + TypeScript + Vite, React Router, TanStack Query, Radix controls and the AI SDK assistant. The existing `web/css` files remain the source of truth for the light/dark game-window theme. Tailwind has no reset.

```sh
cd frontend
pnpm install --frozen-lockfile
pnpm dev
pnpm build
```

React owns every page and its interactions: home, prices and sales, watch lists, collection alerts, assistant/history, account, privacy, contributors, download, browser capture and the item/monster/map/search/route catalogue. There is no legacy-page mount adapter. Existing legacy assets stay available to already-open browser sessions.

Direct catalogue links retain their escaped Rust-rendered first paint and HTTP statuses for indexing and no-JavaScript visitors. The shared React application takes over using `/api/v1/catalog/page`, backed by the same queries and filter normalization. React owns catalogue filters, offer dialogs, instance stats, the flat offer list (lowest price or newest first), ladder, trend and quick previews; it never fetches an HTML fragment to replace the page.

The parser-blocking `boot.js` sets the theme before CSS. React uses the same account-scoped storage facade as watch settings and preferences. Keep initial theme resolution out of a mount effect. URL parameters own filters and sorting; the single market SSE stream invalidates market queries.

The screen reader/worker/structured-upload protocol is unchanged. `web/collect/engine.js` exposes an observable state controller and lifecycle methods; React renders all capture UI. Leaving capture stops tracks, terminates workers, cancels pending upload requests and releases local frame bitmaps. Collector tokens stay in existing storage and authorization headers. Alert history stays separated by hashed collector identity.

Build assets go to `web/react`. Stable revalidated entry files load hashed chunks. Preserve chunks from deployed releases so already-open pages can finish lazy imports. Deploy the matching executable and assets through the existing immutable bundle/supervisor workflow.

The Tools tab opens `/tools`; enhancement planning lives at `/tools/enhancement`, and collection keeps its existing `/alerts`, `/collect/` and download URLs. These collection routes select Tools in the main navigation.

Enhancement uses the selected equipment's CW `tuc` and matching scroll family, structured success rates and stat gains (then English CW descriptions), and compares 10% and 60% scrolls together. The user types a minimum stat gain; overshooting is allowed. Renewal policy iteration minimises total equipment and scroll costs, choosing a scroll or abandonment at every state. The result includes expected equipment and scroll counts and the reachable step-by-step policy. Destructive and special scrolls are unsupported. Equipment quotes require zero successful enhancements and the full original slot count; spent-slot and unparsed equipment are excluded. Prices use the selected 25th, 50th (default median), or 70th percentile of eligible current unit asks, with linear interpolation at `(sample count - 1) * percentile`. Each offer counts once, independent of stock. Equipment eligibility is applied first: only unenhanced full-slot gear participates. Optional original-stat filters match captured numeric values exactly and combine with AND; unknown stat arrays are excluded when filtering, known omitted zero stats count as zero, and no catalogue fallback substitutes for a captured value. These are original absolute tooltip values, not bonuses relative to catalogue defaults. Stat choices come from eligible observed gear; an unavailable combination has no quote and never falls back to mixed gear. Market prices are read-only; the selected percentile and stat filters survive live updates. Missing-price scrolls are explicitly excluded, never priced at zero. Quotes do not guarantee repeat purchases. The expectation assumes independent rolls, consumed slots on failure, immediate stopping at the target and zero resale value for discarded items. Regressions: `node --test web/tests/enhancement.test.mjs`, `node web/tests/enhancement.e2e.mjs`, and the isolated-database Rust `enhancement` test.

Equipment bonus filters compare captured stats with catalogue reference values and exclude physical/magic defence; an enhancement count alone does not qualify. Attribute filters use the actual captured value (default minimum 1), never a catalogue fallback. Equipment cards combine defence rolls when every other stat, enhancement count and remaining-upgrade count matches, showing defence ranges, the combined listing count and the lowest offer price. Individual offer details retain their original stats.

Equipment details follow the game tooltip (`src/components/equipment.tsx`): requirements with zero values dimmed, the five jobs (新手 战士 魔法师 弓箭手 飞侠; MSCW has no pirates; mask 0 lights all five, -1 only 新手), weapon or equipment category, attack speed (2–3 很快, 4–5 快, 6 普通, 7–8 慢), stats in game order and upgrade slots. The item page shows a strip under the head (also in the Rust first paint). Every listing row with captured stats (`data-piece-item` / `data-piece`, set by `OfferRow`) opens that piece's tooltip through the quick preview: hover on desktop (a click pins it on rows without their own link), a bottom sheet on a phone tap. Buttons inside the row keep their own action. The tooltip shows the piece's captured values and a green `(+N)` over the catalogue base, its enhancement count as `(+N)` after the name, the offer's channel, room, shop, owner, price, stock and time under the stats (the phone sheet covers the row), and a link to the item except on that item's own page. Rows no longer expand inline. The quick preview of an item shows the same requirements, jobs and lines as its 装备资料 section, in place of the old base-stat list. Data: `page.equipment` and `page.market.base_stats` from `/api/v1/catalog/page` (see `server/README.md`).

The stat-set header line's bonus-only switch shares the global filter's equipment condition. Switching it off restores all equipment while retaining other conditions; the switch remains available when no offers match.

The item page has one filter dialog. Multiple stat minimums are combined with AND; the old single-stat preference migrates automatically. Attribute and captured/bonus conditions reach the catalogue API before sale pagination and price aggregation. Cards, listing locations and recent sales use the same conditions. Stock conditions apply to current offers only. Equipment offers are grouped by stat set by default (`item.offerView`; 按属性/按报价 switches to the flat list). Each set has a thin header with the stats that differ between sets, upgrade slots, count and lowest price, followed by its offers in the chosen order; a row keeps only what varies inside the set (enhancements and defence rolls), and offers without captured stats come last. Clicking a set header opens `/item/<id>?variant=<id>`: the server resolves the saved instance to its full group, ignoring defence rolls and retaining enhancements and upgrade slots. Quotes, sale samples and seven-day charts are scoped to that group, including after refresh, direct navigation and SSE. Equipment sale rows show time and the shared compact captured-stat summary directly on their second line, without a disclosure or extra action. Missing stats are identified explicitly.

Watch reminders are saved per item alongside its existing manual cap and notification switch, including account sync and guest import. Sold 10/25/50% modes dynamically use the item's trade prices from the last 72 hours (or its latest 20 trades when none), before its manual cap or advanced conditions; the backend alone computes cutoffs (rounded up to the coarsest round number at most 2% higher, e.g. 299 -> 300); the page never recomputes them. Advanced reminder conditions cover minimum unit price, stock and captured equipment attributes; they exclude time windows. Bonus checks use the same catalogue reference stats as item pages and ignore defence-only changes. List browsing filters remain separate from reminder rules. The icon beside the matching count opens `/watch?item=ID#watch-matches`, showing that item's reminder matches without unrelated browsing filters. Counts and details use the returned complete groups; a short status identifies a truncated public feed. Shared and personal notifications use these same item rules and full grouped inventory, with independent seen histories and group deduplication; changing conditions never replays previously seen quotes. The personal percentile feed waits for the shared baseline.

Validation: `pnpm check`, `pnpm build`, `node --test web/tests/*.test.mjs`, and isolated browser fixtures `accounts`, `watch-reminders`, `agent`, `contributors`, `search`, `react-migration`, `react-complete`, `item-offer-filters`, `item-preview-live`, `live-search-focus`, and `equipment-filters` (`.e2e.mjs`). Real candidate/public checks use `THEME_TEST_ORIGIN`, `REACT_VERIFY_ORIGIN` and `FILTER_TEST_ORIGIN` with `theme`, `react-live`, `react-complete-live` and `filter-layout`. Set `PLAYWRIGHT_MODULE` / `PLAYWRIGHT_CHANNEL` for an external Playwright runtime.


Watch alerts are owned by `WatchAlertsProvider` at application scope. Shared offers and personal collector visits reuse one pair of feeds across routes; watch edits take effect immediately and account changes reset notification history. In-page alerts need an open site tab. A signed-in browser can also turn on Web Push from the watch page (`src/lib/push.ts`, `web/sw.js`): the server then matches new offers and pushes alerts while the site is closed, and the page stops showing its own system notifications for watch alerts. See `WEB_PUSH.md`. System notifications go through the service worker, which Android requires. The collector's local gateway keeps page notifications only. Windows/browser notification settings still govern display.

Page memory (`src/lib/page-memory.ts`, per browser tab in sessionStorage): each main navigation tab (首页, 图鉴, 关注, 工具) and the logo return to that section's last page with its URL filters, the price table's loaded rows and the scroll position; the catalogue tab only remembers `/search` lists. Refresh and back/forward restore the scroll position too, retrying briefly while data renders and stopping as soon as the user scrolls. Clicking the tab of the page already shown scrolls to the top; the pages' own clear buttons reset filters. The watch page remembers the selected list. The site search (`src/lib/search-memory.ts`) keeps its text across pages, shows the query of `/search?q=` and has a clear button; with an empty box it lists the last eight searches on this device (submitted or picked), each removable, plus 清除. Regression: `web/tests/page-memory.e2e.mjs`.
